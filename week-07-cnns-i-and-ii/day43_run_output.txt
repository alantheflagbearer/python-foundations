======================================================================
7. POOLING BUDGET -- WHERE A FOURTH BLOCK BREAKS
======================================================================
block 1: input 30x30 -> conv(k=3) -> 28x28 -> pool(2x2) -> 14x14
block 2: input 14x14 -> conv(k=3) -> 12x12 -> pool(2x2) -> 6x6
block 3: input 6x6 -> conv(k=3) -> 4x4 -> pool(2x2) -> 2x2

after 3 blocks, spatial size is 2x2. trying a 4th conv(k=3): 2 - 3 + 1 = 0 -- NOT A VALID SIZE. this is a real, mechanical failure: a 3x3 kernel cannot slide across a 2x2 input even once with no padding. that is the pooling budget, exactly reached.
conv2d_forward_mc actually ran and returned shape (1, 12, 0, 0)

the real fix (used throughout modern CNNs, not implemented here to keep today's from-scratch scope honest): 'same' padding, which pads the input before each conv so spatial size only shrinks at pooling steps, not at every convolution too -- buying more blocks before hitting this wall.

--- ThreeBlockConvNetRGB (f1=3, f2=6, f3=9, hidden=8) ---

HEADLINE RESULT: params 4832 -> 2024 -> 1079 fell steadily (monotonic), but test accuracy went 0.637 -> 0.850 -> 0.512 -- NOT monotonic. Two blocks was the real sweet spot: it beat OneBlock on BOTH axes at once (fewer parameters AND higher accuracy), echoing Day 42's finding. Three blocks kept shedding parameters but gave back the entire accuracy gain and then some, landing below even OneBlock. All three memorized the training set perfectly (train acc 1.000/1.000/1.000), so this is not underfitting -- it is that pooling a 30x30 image down to a 2x2 feature map (Topic 7's pooling budget, one step before it becomes mechanically impossible) leaves too little spatial detail for the dense head to generalize from. Depth's benefit here had a ceiling, and today's honest numbers show exactly where it sat.

9. WHAT THIS MAPS TO IN PYTORCH
======================================================================
from torchvision import transforms
preprocess = transforms.Compose([
    transforms.Resize((64, 64)),                     # PIL resize, Topic 1
    transforms.RandomHorizontalFlip(),                # Topic 2
    transforms.RandomCrop(48),                        # Topic 2
    transforms.ColorJitter(brightness=0.35),          # Topic 2
    transforms.ToTensor(),
    transforms.Normalize(mean=[0.485, 0.456, 0.406],  # Topic 1, per-channel
                         std=[0.229, 0.224, 0.225]),
])

model = nn.Sequential(
    nn.Conv2d(3, 3, 3), nn.ReLU(), nn.MaxPool2d(2, 2),   # block 1
    nn.Conv2d(3, 6, 3), nn.ReLU(), nn.MaxPool2d(2, 2),   # block 2
    nn.Conv2d(6, 9, 3), nn.ReLU(), nn.MaxPool2d(2, 2),   # block 3
    nn.Flatten(),
    nn.Linear(9*2*2, 8), nn.Tanh(),
    nn.Linear(8, 4),
)
nn.Conv2d(3, ...) as the FIRST layer's in_channels is the default in every real vision model, not a special case -- exactly what today's OneBlockConvNetRGB/TwoBlockConvNetRGB/ThreeBlockConvNetRGB hardcode by hand. Real architectures avoid the pooling-budget wall from Topic 7 with padding='same' inside nn.Conv2d.
